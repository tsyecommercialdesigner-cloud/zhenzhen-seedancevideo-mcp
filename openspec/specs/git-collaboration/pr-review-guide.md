# PR 与评审指南

规范性要求见 [spec.md](spec.md)，提交格式见 [commit-guide.md](commit-guide.md)。

## 创建与验证

- 一个 PR 聚焦一个完整目标，标题采用提交格式，描述遵循现有模板，说明问题、行为变化、关联需求、验证和未覆盖项。
- 运行真实配置的测试、类型检查及适用安全扫描；TypeScript 使用锁定工具链。仅当项目实际提供对应 package.json script 和 TypeScript 配置时才采用相关命令，不固定所有项目必须执行 npm test 或临时下载工具。
- 按改动检查注入、秘密、权限、敏感数据、路径越界及依赖风险；AI 辅助评审可以提供线索，但其结论须核验，不能替代测试、工具扫描或人的判断。
- 核对命名、类型、注释、返回契约及错误语义；自动检查覆盖的部分引用检查结果，未覆盖的部分继续评审，不能依据某个 Harness 规则文件跳过。
- 按验收约定检查测试覆盖与失败路径；纯指令 Skills 检查选择、任务行为和回归样例。将实际检查摘要及限制写入 PR，不虚构固定数量的检查结果。

## 评审重点

- 需求、业务逻辑、边界、权限、数据和接口契约是否正确。
- 数据库变更、并发、索引和 N+1 等性能问题仅在实际涉及时评审；HTTP API 按其契约，MCP 按协议，Skills 按任务与输出契约，不统一要求 REST。
- 架构选择是否有备选、理由与影响，是否引入不必要复杂度；提出 Request Changes 时给出具体依据和可执行建议，需要权衡时讨论可行备选。
- 按团队响应时限处理，默认目标为 24 小时；不可达时记录实际安排，不将响应目标伪装为已生效的自动门禁。

## 合入

用户本人、Agent和CI共同评审，不强制其他人批准。必需检查通过、阻塞评论解决、适用checklist据实完成后才按授权合入；检查关联当前实际内容及相关输入，不伪造审批或绕过现行规则。
feature/* → dev → main；dev可积累多个功能。合并后按差异复验，不强制全量重跑；CD仅实际发布时执行。评审通过不等于获得合并、推送或发布授权。
